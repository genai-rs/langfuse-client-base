# langfuse-client-base 0.19.0 → 0.20.0: nullable OpenAI token-detail counts

This release generates with `timvw-rust` 0.22.0. The Langfuse spec (`openapi.yml`) and openapi-generator (7.27.0) are
unchanged. The machine-readable census is `api-diff-0.19.0-to-0.20.0.json` in this folder (`compare_public_api.py`
against 0.19.0). The generator's own guide, [migrating from 0.21 to 0.22](https://github.com/timvw/openapi-generator-timvw-rust/blob/main/docs/guides/migration.md#from-021-to-022), shows every change with
the code before and after.

`timvw-rust` 0.22.0 does not change the generator configuration, so `scripts/generate-openapi-client.sh` only changes
its image tag.

## What stays the same

- Every model, field and enum except the four fields below. No type is added, removed or renamed.
- Every operation keeps its module, function name and parameters.
- The JSON bodies sent, and every JSON body received that decoded before.

## What changes

**OpenAI token-detail counts can be null.** The `*_tokens_details` maps of the two OpenAI usage schemas (restored from
`scripts/legacy_v3_compatibility.json`) declare `additionalProperties: {type: integer, nullable: true}`. The nullable
values were ignored, so a body such as `{"prompt_tokens_details": {"cached_tokens": null}}` failed to decode. The values
are `Option<i64>` now:

| Model | Field | Before | After |
| --- | --- | --- | --- |
| `OpenAiCompletionUsageSchema` | `prompt_tokens_details` | `Option<Option<HashMap<String, i64>>>` | `Option<Option<HashMap<String, Option<i64>>>>` |
| `OpenAiCompletionUsageSchema` | `completion_tokens_details` | `Option<Option<HashMap<String, i64>>>` | `Option<Option<HashMap<String, Option<i64>>>>` |
| `OpenAiResponseUsageSchema` | `input_tokens_details` | `Option<Option<HashMap<String, i64>>>` | `Option<Option<HashMap<String, Option<i64>>>>` |
| `OpenAiResponseUsageSchema` | `output_tokens_details` | `Option<Option<HashMap<String, i64>>>` | `Option<Option<HashMap<String, Option<i64>>>>` |

A `None` value serializes as `null`, and `validate()` skips it. The `new` constructors do not take these fields, so
their signatures do not change.

**`lib.rs` allows `clippy::type_complexity`.** Every client generated by `timvw-rust` 0.22.0 gets
`#![allow(clippy::type_complexity)]`, for the deeper nested types the release can emit. It only affects lints inside
this crate; nothing changes for callers.

## Migrating

- Code that builds these maps wraps each count in `Some(..)`:
  `HashMap::from([("cached_tokens".into(), Some(1))])`.
- Code that reads them handles the `Option` of each value, e.g. `.values().flatten()` to skip the nulls, or
  `.filter_map(|(k, v)| v.map(|v| (k, v)))` to keep the keys.
